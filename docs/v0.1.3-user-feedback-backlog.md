# EdgeEnv First-user Feedback Backlog

> Language: [English overview](language.md#english-overview) | [한국어/원문](#)

## 1. WHAT — 이 문서가 정하는 것

현재 README 시작 경로를 따라가는 사용자가 어디서 막히는지 수집하고, 다음 후보 릴리스에 묶을 만한 작은 사용성 개선을 고르는 기준이다.

이 문서는 feature roadmap이 아니다. README Quickstart, local command 연결, compare 판단, optional Jetson 문서 흐름에서 나온 질문을 같은 형식으로 모아 다음 작은 개선 후보를 고르는 backlog다.

## 2. CONTENTS — 수집할 질문

Collect feedback about:

- install or entrypoint confusion
- fake run command failures
- local command contract questions
- missing or unclear example config paths
- `report compare` interpretation questions
- resource metrics lookup confusion
- Jetson setup or repeated measurement friction
- export/import or bundle handoff questions

Do not collect requests for unsupported scope here:

- remote SSH runner implementation
- Docker, WSL, VM, cloud execution
- dashboard, leaderboard, login/auth
- model or dataset upload service
- composite score or ranking

## 3. HOW — 수집 방식

Preferred intake:

1. Ask the user to start from README's current `Start Here` path.
2. Ask for the first command or document section that was confusing.
3. Ask whether the issue blocked progress or only slowed interpretation.
4. Capture the exact command, output, OS/Python version, and whether the run used fake, local, or Jetson-local execution.
5. Label the issue by the first blocked path: `install`, `fake-run`, `local-command`, `compare`, `resource-query`, `jetson-docs`, or `export-import`.

Use the GitHub issue template:

- [README Quickstart Feedback issue](https://github.com/gwonxhj/InferEdgeEnv/issues/new?template=readme-quickstart-feedback.md)
- [Template source](../.github/ISSUE_TEMPLATE/readme-quickstart-feedback.md)
- [Feedback Template Rehearsal](v0.1.3-feedback-template-rehearsal.md)

## 4. HOW NOT — 피해야 할 함정

- Do not treat every question as a feature request.
- Do not expand MVP scope just because a user asks for remote execution.
- Do not change result schema, `metadata.json`, `result.json`, or compare output while triaging wording feedback.
- Do not make resource metrics part of comparability or ranking.
- Do not rewrite old release documents unless they actively mislead the current first-start path.

## 5. WHERE — 정리 위치

Use these locations:

- README first screen: only the shortest feedback pointer
- `docs/release-follow-up-v0.1.4.md`: current release trust path and feedback intake pointer
- GitHub Issues: one issue per blocked user path
- Future polish branch: only after repeated feedback points to the same friction

Current v0.1.5 candidate observations:

- Keep the README feedback link label release-neutral so the first screen does not look stale after a new baseline release.
- Keep the issue template release-neutral in `about`, while the scope check names the current release baseline.
- Clean-room README Quickstart passed on `v0.1.4`; the only non-blocking friction observed was that `report bundle-summary` requires `--scenario <label>:<run_id_a>:<run_id_b>`.
- The same bundle-summary `--scenario` confusion was reproduced once more, so `docs/portfolio-demo-path.md` now states that bundle summaries are pair/scenario reports rather than single-run positional reports.
- Portfolio Demo Path local-only reviewer flow was re-run on 2026-05-14 from an isolated demo root: fake evidence, adapter boundary, same-condition compare, export/import, imported compare, and bundle-summary all passed. No new v0.1.5 usability friction was observed.
- Treat repeated first-run confusion as a documentation or CLI-message polish candidate before considering new feature work.

Release note candidate:

- Theme: first-user documentation polish only.
- Mention: README/Korean README feedback intake stayed release-neutral, clean-room README Quickstart passed on `v0.1.4`, and Portfolio Demo Path now clarifies the `report bundle-summary --scenario <label>:<run_id_a>:<run_id_b>` pair format.
- Do not claim: new CLI behavior, new schema support, changed compare output, changed export/import format, changed sampler behavior, or new target support.
- Validation to cite later: `python -m inferedge_env.cli doctor`, `python -m pytest -q`, and GitHub Actions readiness on Python 3.10/3.11 from the related documentation PRs.

## 6. WHY — 배경 판단

`v0.1.4` already tightened the evidence contract, adapter template, schema policy, demo path, CLI error guidance, and release quality gate. The next best signal is not another feature; it is whether a new user can move from README to a fake run, local command run, compare report, and optional Jetson-local evidence without hidden assumptions.

Feedback should preserve EdgeEnv's product boundary: local run evidence registry, artifact portability, and comparability judgement.

## 7. ⚠️ LEARNED CAUTIONS — 학습된 주의사항

- User feedback after a polish release should identify the first blocked path before proposing new implementation work.
