# EdgeEnv v0.1.3 Candidate Plan

## 1. WHAT — 이 문서가 정하는 것

`v0.1.2` 이후 다음 안정화 릴리스 후보를 작은 개선 묶음 네 개로 정리한다. 목표는 새 target이나 leaderboard 같은 큰 기능이 아니라, 첫 사용자가 README와 local evidence loop를 더 안정적으로 따라가게 만드는 것이다.

이 문서는 implementation spec이 아니라 작업 순서 가이드다. 각 단계는 별도 브랜치와 PR로 진행하고, 한 단계가 끝나면 tests, PR, merge 후 다음 단계로 넘어간다.

## 2. CONTENTS — v0.1.3 후보 순서

Recommended order:

1. **Install / Quickstart Resilience**
2. **README Quickstart Command Consistency**
3. **Resource Query UX Refinement**
4. **Release Maintenance Checklist**

Release theme:

```text
v0.1.3 = first-user polish release
```

Release rehearsal:

- [EdgeEnv v0.1.3 Release Rehearsal](v0.1.3-release-rehearsal.md) confirms the required local gate, README smoke, resource query portability, compare/report smoke, and failed-run portability before the version bump/tag branch.

## 3. HOW — 단계별 진행 기준

### 1. Install / Quickstart Resilience

Branch:

```text
docs/install-quickstart-resilience
```

Goal:

- make `python -m pip install -e ".[dev]"` failures easier to triage
- explain no-network/build-dependency failures without making them look like EdgeEnv runtime failures
- keep the first README path friendly for clean venv users

Expected scope:

- README install troubleshooting pointer
- packaging/entrypoint troubleshooting table
- clean-room rehearsal note cross-link
- no CLI/schema/artifact contract changes

Validation:

- `python -m pytest -q`
- `git diff --check`
- `python -m inferedge_env.cli doctor`
- `edgeenv doctor`

### 2. README Quickstart Command Consistency

Branch:

```text
docs/readme-quickstart-consistency
```

Goal:

- reduce duplicated README entry paths
- make fake run -> local command -> compare -> Jetson docs flow easier to scan
- keep the first screen short and release-aware

Expected scope:

- README wording and section order
- Guide Map ordering
- links to clean-room and follow-up notes
- no product scope expansion

Status:

- Completed by moving detailed commands into Quickstart, making the first screen a short path selector, and ordering Guide Map links around install, clean-room validation, follow-up, and v0.1.3 planning.

### 3. Resource Query UX Refinement

Branch:

```text
registry/resource-query-ux
```

Goal:

- improve repeated use of `runs resources list` only if it stays clearly supplemental
- preserve artifact-first resource metrics policy

Candidate scope:

- optional JSON output
- clearer source/unit display
- source summary if it remains lookup-only
- tests for source and imported registry behavior

Status:

- Completed by adding `runs resources list --json`, explicit supplemental lookup notes, source count display, and source/imported registry JSON tests while keeping `result.json` canonical.

Hard boundary:

- no ranking
- no composite score
- no resource metrics as comparability gates
- no canonical migration away from `result.json`

### 4. Release Maintenance Checklist

Branch:

```text
docs/release-maintenance-checklist
```

Goal:

- make the next release repeatable
- collect local tests, clean-room rehearsal, optional Jetson smoke, tag, and GitHub Release steps in one place

Expected scope:

- release maintenance checklist doc
- links from handoff/release rehearsal docs
- no release automation unless separately requested

Status:

- Completed by adding `docs/release-maintenance-checklist.md` and linking it from README/doc guides as a repeatable local, clean-room, optional Jetson, tag, and GitHub Release gate.

## 4. HOW NOT — 피해야 할 함정

- Do not turn v0.1.3 into SSH/Docker/WSL/cloud target work.
- Do not add public leaderboard, upload server, auth, dashboard, or composite ranking.
- Do not change `result.json`, `metadata.json`, export manifest, registry semantics, or compare output labels without a migration plan.
- Do not let resource metrics become a direct comparability requirement.
- Do not merge any step if tests or CI fail.

## 5. WHERE — 다른 문서와의 관계

- **README Quickstart Clean-room Rehearsal**: supplies the install friction that motivates step 1.
- **Packaging And Entrypoint Readiness**: owns install/doctor troubleshooting.
- **v0.1.2 Follow-up Note**: describes the current release baseline that v0.1.3 should polish.
- **V1 Handoff Status**: keeps current capability and next-work guidance.
- **Registry Resource Query Design**: constrains step 3.
- **Release Rehearsal**: feeds step 4.
- **v0.1.3 Release Rehearsal**: records the actual checklist pass before release branch/tag work.

## 6. WHY — 배경 판단

`v0.1.2` already closed release, Jetson, README, and clean-room validation. The next useful release should therefore improve first-user confidence instead of adding a broad new execution surface.

The sequence intentionally starts with install and README polish before touching CLI behavior, because every later feature depends on users entering the project successfully.

## 7. ⚠️ LEARNED CAUTIONS — 학습된 주의사항

- v0.1.3 candidate work should proceed in the documented order unless a real user-facing blocker appears; this keeps polish work from fragmenting into tiny unrelated PRs.
